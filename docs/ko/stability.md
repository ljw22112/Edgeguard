# MEC 앱 안정성: 고장 주입 장기 실행 시험

[← README](../../README.ko.md) · [English](../stability.md)

[`tools/soak_test.py`](../../tools/soak_test.py)는 MEC 앱을 별도 프로세스로 띄워 ACME IN-CSE와 몇 분 동안 돌립니다. 작업자 태그 6개와 지게차 모듈 3개가 각자 자기 AE로 CSE에 5 Hz로 게시합니다. 지게차는 세 통로를 오가고 작업자는 계속 가로질러 경보가 끊임없이 발생합니다. 장치 자리의 수신기가 경보를 종단 간으로 받습니다(장치 샘플 → CSE → MEC 앱 → CSE → 장치). MEC 앱과 장치는 로컬 프록시를 거쳐 CSE에 붙으므로 연결을 끊을 수 있습니다.

고장을 차례로 넣습니다.

| 고장 | 내용 |
|---|---|
| 폭주 | 스레드 8개가 `/notify`로 알림 2,000건을 바로 보냄. 3분의 1은 잘못된 형식(JSON 아님, NaN, 잘못된 타입, 200 kB 문자열) |
| 카메라 변동 | 카메라가 30초 동안 매 프레임 새 위치의 사람 3명을 보고. 다시 잊어야 할 미태그 트랙 수백 개 |
| 단절 | CSE와의 연결을 10초 끊음 |
| 상태 유실 | CSE의 모든 AE · 컨테이너 · 구독을 삭제(DB 없이 복원한 상황). 장치는 404를 보고 다시 등록 |
| WAN | 클라우드 복사본 주소가 내내 닿지 않음 |

## 찾은 문제와 수정 ([`mec_app/app.py`](../../mec_app/app.py))

| 찾은 문제 | 수정 |
|---|---|
| **CSE가 상태를 잃은 뒤 경보가 다시는 태그에 가지 않았습니다.** MEC 앱 자신의 AE와 alert / control / risk 컨테이너가 사라졌는데 404만 기록했습니다. 하트비트도 끊겨 모든 지게차가 서행했습니다. | 자기복구 트리: 쓰기에서 컨테이너가 없으면 AE와 컨테이너를 다시 만들고 재시도합니다. 장치가 하나씩 다시 등록하므로, 이후 2분 동안 3초마다 구독을 다시 겁니다(복구 모드). |
| 장치 데이터는 60초 주기 구독 점검이 우연히 돌 때에야 돌아왔습니다(이번 실행 11초, 최대 60초). | 쓰기 실패 뒤 CSE가 다시 응답할 때, 트리를 다시 만들었을 때, 또는 장치가 살아 있었는데 8초 동안 아무 소식이 없을 때 복구 모드로 들어갑니다. |
| 예외가 난 백그라운드 루프는 그대로 멈췄습니다. 하트비트, 게시, 구역 방송, MEC-IPE 감시가 조용히 사라졌습니다. | 모든 루프가 감독기 아래에서 돌고, 예외를 기록한 뒤 다시 시작합니다. `/health`가 루프별 재시작 횟수와 마지막 동작 이후 시간을 보여 주고, 멈춘 루프가 있으면 `degraded`로 알립니다. |
| 알림 폭주 때 위험 평가가 웹 서버 스레드풀을 차지했습니다. 이번에 `/health`가 358 ms, 앞선 실행에서는 5초 넘게 걸렸습니다. | `/notify`는 즉시 답하고 큐에 넣습니다. 작업자 하나가 위험 엔진을 돌립니다. 같은 장치의 더 새 샘플이 대기 중인 옛 샘플을 대체하므로 지연이 한정되고, CSE가 느린 알림 응답을 보지 않습니다. |
| 카메라 `untagged_N` ID가 남긴 WAIT 표시, STEP ASIDE 타이머, 구역 타이머가 계속 쌓였습니다. | 잊힌 트랙의 부가 테이블도 정리하고, `/health`가 모든 테이블 크기를 보여 줍니다. |

클라이언트도 두 군데 고쳤습니다([`edgeguard/onem2m.py`](../../edgeguard/onem2m.py)). ACME가 이미 있는 AE에 "발신자 이미 등록됨(4117)"으로 답하는 경우를 "이미 있음"으로 처리하고, 다른 클라이언트가 같은 순간 만들고 있는 구독은 재시도합니다.

## 결과 (4분, 같은 하네스)

| | 수정 전 | 수정 후 |
|---|---|---|
| 검사 통과 | 10 / 14 | **14 / 14** |
| CSE 상태 유실 뒤 경보가 태그에 다시 도착 | **안 됨**(남은 50초 안에 끝내 복구 안 됨) | **2.1초** |
| CSE 상태 유실 뒤 장치 데이터 복구 | 11.1초 | **2.1초** |
| 10초 단절 뒤 데이터 · 경보 복구 | 1.4초 | 1.3초 |
| 가장 느린 `/health` 응답(폭주 포함) | 358 ms | **112 ms** |
| 최대 스레드 수 | 17 | 9 |
| 워밍업 뒤 메모리 증가 | 3.4 MB | 2.4 MB |
| 평상시 종단 간 경보 지연 (p50 / p95) | 87 / 134 ms | 94 / 139 ms |
| `/health`로 루프 · 테이블 상태 확인 | 불가 | 가능 |

CI가 매 커밋 이 시험을 3.5분 동안 돌립니다. 같은 종류의 고장(통신 불량, MEC 재시작)에서의 안전성은 [robustness.md](robustness.md)에 있습니다.

## 고장 상황에서 본 ACME 동작

ACME 2026.05.3의 동작 세 가지가 고장을 키웠습니다. ACME 프로젝트용으로 [forum/acme-issues.md](../forum/acme-issues.md)에 정리했습니다.
- ACME가 아직 시작 중일 때 요청이 들어오면 시작 자체가 중단됩니다("add_url_rule can no longer be called"). 장치가 계속 보내는 현장에서는 재시작한 CSE가 뜨지 못합니다.
- 구독의 알림 대상이 닿지 않을 때 AE를 지우면 구독이 남을 수 있습니다. 다시 만들면 409 "이미 있음", 갱신하면 404가 납니다.
- 같은 AE를 같은 순간 만들고 지우면 AE 없이 발신자 등록만 남을 수 있습니다. 이후 등록은 모두 4117이 납니다.
